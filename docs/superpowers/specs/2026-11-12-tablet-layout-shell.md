# Specification: 平板外壳基于布局树重写（Tablet Shell on the Layout Tree）

## Metadata

- **Version**: 0.1.0
- **Status**: Draft
- **Author**: agent（与用户讨论中）
- **Created**: 2026-11-12
- **Last Updated**: 2026-11-12

## Overview

平板（mobile shell）目前有一条**独立于桌面外壳**的窗口几何路径：`mobile_window_geometry()` 里硬编码“全屏减状态栏”和“半屏减边距”，分屏是额外的特例结构（两个窗口 id + 比例），客户端不接受该尺寸时由外壳用 `BoxFit` 缩放兜底。

这条路径已经导致多类 bug：后加入分屏的应用按旧尺寸渲染并被缩放到 50%、输入映射出现 45 逻辑像素偏移、分割条拖拽卡在预览态、退出入口缺失等。

本规范的目标是**取消这条独立路径**，让平板复用桌面外壳已经在用的「布局树拥有几何」模型：合成器持有布局树并负责每个窗口的矩形（含最小尺寸约束），外壳只按发布出来的几何 1:1 绘制与映射输入，不再自行缩放。

## Requirements

### Functional Requirements

- **FR-1 单一几何来源**：平板上任何窗口的矩形只由合成器的布局树决定；外壳不得自行计算、裁剪或缩放窗口矩形。
- **FR-2 全屏单应用**：未分屏时，应用占据状态栏以下的整个手机屏；行为与当前一致。
- **FR-3 分屏即布局树节点**：分屏等于在手机工作区插入一个 `Split` 节点（横屏左右、竖屏上下，默认 50:50）。不引入第二套“分屏状态”。
- **FR-4 最小尺寸约束**：建立分屏、改变比例、旋转时，布局结果必须满足两侧客户端声明的最小尺寸；无法满足时**不得建立/保持该布局**，并向用户给出可读原因（规范 §7：「该应用最小需要 W×H」）。
- **FR-5 不做内容缩放**：窗口内容一律按几何 1:1 绘制（含 buffer 缩放），禁止 `BoxFit.cover/contain` 之类的“适配”缩放。
- **FR-6 输入跟随几何**：每个窗口的输入区域由同一份几何推导，触摸坐标与客户端表面 1:1；不存在状态栏/装饰带来的偏移。
- **FR-7 分屏入口**：仍为 recents 长按拿起 → 40/20/40 放置区；中间 20% 取消。
- **FR-8 第二侧选择器**：仍为缩略图网格；放不进当前窗格的应用置灰并显示原因（FR-4）。
- **FR-9 配对卡片**：recents 中一棵 `Split` 子树 = 一张卡片；上划关闭两侧，点按回到分屏且激活侧为离开时的那一侧。
- **FR-10 退出分屏**：必须存在至少一个明确入口（返回键作用激活侧、配对卡片上划、或新的显式操作）。
- **FR-11 键盘**：软键盘只作用于激活侧；非激活侧几何不变。键盘不改变布局树。
- **FR-12 旋转**：输出宽高比变化时，`Split` 的轴随之翻转，比例与成员保持；旋转过程不得产生重复 configure。
- **FR-13 桌面/外接屏不回归**：插入显示器时桌面外壳行为不变；平板布局只作用于手机输出。
- **FR-14 自愈**：客户端暂时不接受新尺寸时，布局保持目标矩形并可重试；不得永久停留在旧尺寸，也不得因此缩放内容。

### Non-functional Requirements

- **NFR-1 可回滚**：新路径以开关或分阶段提交落地，任一阶段可单独回退到当前行为。
- **NFR-2 可测试**：几何与最小尺寸计算必须是纯函数/纯数据，能用单元测试覆盖（Rust + 纯 Dart）。
- **NFR-3 无重复实现**：手机与桌面共用同一套布局树、最小尺寸、输入发布与 1:1 绘制代码；移动端只保留 IME/键盘桥接。
- **NFR-4 性能**：建立/退出分屏不引入额外的全屏重绘；旋转时分屏只 reconfigure 两个成员各一次。
- **NFR-5 一致性**：外壳发布给 Flutter 的 `geometry`、输入区域、绘制区域三者必须由同一份数据派生，避免再次出现“画在一处、点另一处”。

## 术语

| 术语 | 含义 |
|---|---|
| 布局树 | 合成器持有的窗口布局结构：`Window` / `Split{axis, ratio, first, second}` / 滚动列 |
| 几何 | 合成器为窗口决定的矩形（`window.geometry`），外壳唯一的绘制/输入依据 |
| 最小尺寸 | 客户端通过 xdg 声明的最小窗口尺寸（逻辑像素，已乘应用缩放） |
| 激活侧 | 分屏中获得焦点的一侧，接收键盘、返回键与通知点击 |
| 适配缩放 | 外壳为了“塞进”某矩形而自行缩放内容；本规范**禁止** |

## 现状与目标

### 现状（问题来源）

| 位置 | 现状 | 后果 |
|---|---|---|
| `mobile_window_geometry()` | 硬编码全屏/半屏几何，不看最小尺寸 | 给出客户端做不到的尺寸 |
| 分屏模型 `MobileSplit{first,second,ratio}` | 与布局树平行的一套状态 | recents、输入、键盘各自维护同步 |
| `WindowTextureRect` 的 `cover/contain` | 外壳替客户端“适配” | 小字、裁切、点击错位 |
| 输入区域计算 | 外壳按 cover 比例重算 | 与绘制不一致（曾偏差 45px） |
| 分割条 | 外壳私有交互 | 拖拽状态可残留，退出入口不稳定 |

### 目标（引用现有实现）

- 布局树：`compositor/src/bin/deniald/window_layout.rs`（`Split{axis,ratio,first,second}`、`minimum_size()`、`arrange()`、滚动列）。
- 1:1 绘制：`desktop_window_frame.dart` 的 `WindowPlane.texture(...)`（按几何排布，按 `presentationScale` 映射 buffer）。
- 输入：`reference_input_layout_coordinator` 由几何推导每个窗口区域。

## 迁移阶段（每阶段独立可验证）

1. **几何并入布局树**：手机输出获得一个布局根（全屏工作区，状态栏作为 inset），全屏单应用状态由布局树产出矩形，结果与现状完全一致。
2. **分屏改为布局操作**：`SplitWindows / UpdateSplitRatio / EndSplit` 转为“插入/调整/删除 `Split` 节点”；最小尺寸不满足时拒绝并回传原因。
3. **外壳 1:1 化**：删除手机路径上的 `cover/contain`；按几何绘制；输入区域改为几何推导；删除旧的偏移补偿。
4. **recents/选择器适配**：配对卡片来自布局子树；选择器按 FR-8 置灰并显示原因。

## Test Steps

1. **全屏回归**：打开 Firefox / 终端 / 文本编辑器，确认铺满状态栏以下区域，文字为原始尺寸，点击位置与视觉一致。
2. **建立分屏（左）**：recents 长按应用 → 拖到左 40% → 选择第二个应用；两侧均为 1:1 原始尺寸。
3. **建立分屏（右）**：拖到右 40%；应用留在右侧、选择器在左侧；标题与方向一致。
4. **最小尺寸拒绝**：把应用缩放设为 1.5 倍（最小宽度变大）后尝试分屏；不符合时应提示「该应用最小需要 W×H」，且不进入半屏。
5. **输入映射**：分屏后分别点击左右窗口的标题栏、内容顶部、右下角按钮；命中位置正确，无 45px 级偏移。
6. **键盘**：点激活侧输入框→键盘只推该侧；点另一侧→键盘跟随，非激活侧几何不变。
7. **返回键**：连续返回只作用于激活侧。
8. **配对卡片**：分屏中进 recents → 只有一张卡片；点按回分屏（激活侧不变）；上划关闭两个应用。
9. **旋转**：分屏中横竖屏切换各 3 次；轴翻转、比例保持、无重复 configure、无黑边。
10. **客户端不配合**：用一个已知拒绝 configure 的客户端（如当前 kgx）重复步骤 2；应停留在目标矩形并自愈重试，**不得**出现内容缩放。
11. **外接屏**：插入显示器，手机与桌面各自工作；拔掉后手机布局完好。
12. **自动化**：布局树与最小尺寸的单元测试（Rust），几何纯函数的 Dart 测试；`cargo test` 与 `dart test` 全绿。

## Acceptance Criteria

- 上述 Test Steps 全部通过；任何一步都不出现“内容被缩放/裁切/点击错位”。
- 平板与桌面**共用**布局树、最小尺寸、输入发布、1:1 绘制代码；移动端专属代码只剩 IME/键盘、状态栏、recents/选择器。
- 客户端拒绝尺寸时，UI 不缩放内容、不永久卡在旧尺寸，并且用户能看到原因（分屏被拒绝时）。
- 删除分割条后，退出分屏至少有两条可用路径（返回键 + 配对卡片上划）。
- 无回归：全屏单应用、recents、桌面布局、外接屏、键盘的既有验收项保持通过。

## 待讨论问题

1. **分屏入口的最终形态**：保留“长按拿起 + 放置区”，还是像 GNOME 那样简化为“拖到边缘自动 tiling”（拖到屏幕左/右边缘松手即分屏，不再需要第二侧选择器）？
2. **第二侧选择器的取舍**：GNOME 没有选择器；是否需要保留缩略图选择器（FR-8），还是直接用“拖第二个应用到另一侧”？
3. **比例交互**：去掉分割条后是否需要新的比例入口（例如拖动两窗格交界处的窄条），还是固定 50:50？
4. **最小尺寸不满足时的策略**：拒绝分屏（FR-4，推荐）／自动把应用缩放降为 1.0（例如 Firefox 957→638）／允许后按 1:1 裁切。
5. **激活侧的视觉表达**：现在完全没有提示；是否需要一个 1px 强调线或阴影？
6. **退出分屏的显式入口**：状态栏按钮／返回键长按／配对卡片，选哪个（或都保留）？
7. **应用缩放与分屏的关系**：分屏内强制 1.0 是否可作为长期策略（退出恢复），还是应该由用户设置决定？
8. **是否保留 v3 的卡片视觉**：本规范按“直接半屏”撰写；若以后想回到卡片+间隙，是否只是外观层的可选主题？
